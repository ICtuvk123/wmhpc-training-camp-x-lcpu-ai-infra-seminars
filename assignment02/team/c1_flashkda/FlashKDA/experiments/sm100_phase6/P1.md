# P1: seed the recurrent state into TMEM

The experiment computes one update:

```text
C[128,128] = S[128,128] + K^T[128,16] @ U[16,128]
S and C: FP32; K^T and U: BF16; accumulation: FP32
```

`tcgen05_p1.cu` starts from the early-allocation-permit-release P0 variant.
It transfers S from global memory through one copy atom's register fragment
at a time into the actual TMEM MMA accumulator. The first MMA accumulates
into this initialized state. This exercises state participation in TMEM;
there is no register epilogue addition of S.

`baseline_p1.cu` uses the existing SM80 MMA atom and tile mapping, loading S
into each register accumulator before its MMA. Both implementations share
`p1_runner.cuh` for inputs, reference, validation, and CUDA event timing.

Each CTA reads its own row-major S tile and writes its own C tile. K^T and U
are shared inputs across the grid, as in P0. S and C are separate allocations:
warmup and timing iterations each perform the same single update. Neither
implementation keeps state across launches. Repeated updates within one CTA
belong to P3; decay belongs to P2. Production K2 and the P0 kernels are unchanged.

## Synchronization and resource contract

- Allocate 128 TMEM columns and release the allocation permit early.
- Map the state with the CuTe TMEM store atom's partition, then wait for all
  TMEM stores. Each transfer uses a small temporary register fragment.
- Publish the SMEM operands to the asynchronous proxy. Order the state stores
  across threads with tcgen05 fences and a CTA barrier before issuing MMA.
- Commit and wait for MMA completion, fence before TMEM readback, and wait for
  TMEM loads before storing C. Deallocate after all consumer warps finish.

The state introduces no SMEM array. The tcgen05 shared-storage structure is
8,320 bytes (8.125 KiB); baseline storage is 8,192 bytes. Note the unit:
8,320 bytes is 8.32 **decimal kB**, not 8.32 KiB.

References: NVIDIA's [tcgen05 synchronization patterns](https://docs.nvidia.com/cuda/archive/13.0.2/parallel-thread-execution/index.html#tcgen05-memory-consistency-model)
and CUTLASS `include/cute/atom/copy_traits_sm100.hpp` (`make_tmem_copy` and
`SM100_TMEM_STORE_32dp32b1x`), plus `include/cutlass/arch/barrier.h` for the
TMEM wait operations. The architecture guard requires enabled TMEM support;
the generic PTX fallback traps instead of emitting architecture-only fences.

## Build and run on B300

CUDA 13.0+, the CUTLASS headers, and a matching B300/SM103 device are required.
For B200 use `--arch sm_100a`. Windows builds need an x64 Visual Studio developer
shell. `--nvcc` and `--cutlass` accept explicit tool and checkout paths.

```bash
python experiments/sm100_phase6/benchmark_p1.py --dry-run
python experiments/sm100_phase6/benchmark_p1.py --build-only

# Builds both implementations, runs regressions, then measures five repeats.
python experiments/sm100_phase6/benchmark_p1.py --batch 1024 --warmup 30 --iters 200 --repeats 5

# Collect achieved occupancy separately from the unprofiled event timings.
python experiments/sm100_phase6/benchmark_p1.py --batch 1024 --ncu ncu
```

Use the exact P0 batch and timing settings for the P0/P1 comparison. Sweep
batch sizes separately to distinguish launch overhead from throughput. A
state tile per CTA increases the memory working set; include that cost when
interpreting the P1/P0 latency change.

The runner writes `build/p1_results.json`, `build/p1_results.md`, build logs,
and optional NCU CSV logs. The Markdown table compares **equivalent P1 baseline
and tcgen05 work**. It reports correctness, latency, SMEM, registers, spills,
TMEM columns, estimated maximum CTAs/SM, and achieved occupancy. Achieved
occupancy remains `unmeasured` without NCU; CUDA occupancy estimates are never
presented as measurements. Spill byte counts come from PTXAS; a `--skip-build`
run reports them as unknown rather than attributing an old log to a new binary.
NCU's event timing is not used in the latency comparison.

## Correctness and sanitizer coverage

Before timing, both executables run 60 regressions each: 30 cases at batch 1
and 3, including zero-product state preservation, zero/nonzero/random S,
off-diagonal one-hot probes over every reduction index and warp/tile boundary,
dense binary-fraction inputs, and three random seeds. Tagged S carries row,
column, and CTA information with precision finer than BF16. The CPU oracle
uses the actual BF16 operands with higher-precision arithmetic and rounds the
final result to FP32. Deterministic cases require exact equality; random
updates use `atol=rtol=1e-5`. Every output CTA and the unchanged input state
are checked, including after multiple launches.

```bash
python experiments/sm100_phase6/check_p1.py experiments/sm100_phase6/build/tcgen05_p1 --impl tcgen05
python experiments/sm100_phase6/check_p1.py experiments/sm100_phase6/build/baseline_p1 --impl baseline
python experiments/sm100_phase6/check_p1.py experiments/sm100_phase6/build/tcgen05_p1 --impl tcgen05 --sanitizer compute-sanitizer --tool memcheck
```

On Windows add `.exe` to executable names. Repeat with `--tool racecheck`,
`synccheck`, and `initcheck`; check baseline with the same tools.

Host-side harness checks (no GPU required):

```bash
python -m unittest discover -s experiments/sm100_phase6 -p test_p1_harness.py -v
```

## Validation status (2026-09-07)

Both P1 sources compiled with local CUDA 13.0 for `sm_103a`, using the existing
cached CUTLASS headers. PTXAS reports:

| Metric | P1 baseline | P1 tcgen05 |
|---|---:|---:|
| Registers/thread | 40 | 154 |
| Spill stores / loads (bytes) | 0 / 0 | 0 / 0 |
| Stack frame (bytes) | 0 | 0 |
| SMEM storage (bytes, source layout) | 8192 | 8320 |
| TMEM columns (source allocation) | 0 | 128 |
| GPU correctness | Unmeasured | Unmeasured |
| Latency | Unmeasured | Unmeasured |
| Achieved occupancy | Unmeasured | Unmeasured |

The seven host harness tests passed. The local machine has an RTX 4060;
attempting a CUDA 13 binary failed during runtime initialization, before
launching the kernel. No Blackwell numerical, sanitizer, latency, or occupancy
result is claimed. P0's user-reported 80 us and 14.73% are comparison references,
not evidence that P1 preserves those results.

After P1 passes on Blackwell, proceed to P2 (`S_old * g + K^T U`). P2 is the
GO / NO-GO gate: measure whether decay and any TMEM/register round trip erase
the advantage over equivalent existing Phase-6 work. A GO supports P3 and
subsequent K2 integration/comparison.
