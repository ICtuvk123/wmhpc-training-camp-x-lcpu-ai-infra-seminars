# P3: register-resident recurrence

`tcgen05_p3_recurrence.cu` extends P2-epi to compute

```text
S[t+1][b,m,n] = S[t][b,m,n] * g[t,b,m] + (K[t]^T U[t])[m,n]
```

It loads FP32 `S_0` once per CTA, retains that state in a distributed register
fragment for all steps, and stores FP32 `S_N` once. A single 128-column TMEM
allocation holds only the current BF16-input, FP32-accumulated product.
Shared memory stages each step's K/U operands. Production K2 is unchanged.

## Why this experiment

The user reports these means from five interleaved rounds in the same session:

| Stage | Mean launch latency, us |
|---|---:|
| P0: K^T U | 80.61 |
| P1-epi: S + K^T U | 132.37 |
| P2-epi: S*g + K^T U | 132.42 |

These supersede the earlier cross-run ~77 us comparison for this decision.
The observed P2-P1 difference is only 0.05 us; the 51.76 us P1-P0 difference
motivates amortizing state movement across steps. This evidence does not
separate state reads, state-fragment lifetimes, and residency effects.
Raw target measurements were supplied by the user, not reproduced locally.

## Data and lifetime contract

- `kt`: BF16 `[steps,128,16]`; `u`: BF16 `[steps,16,128]`.
  All CTAs share these operands, preserving the P2 microbenchmark contract.
- `g_total`: FP32 `[steps,batch,128]`, broadcast over output columns.
- Initial/final state: separate FP32 `[batch,128,128]` allocations.
- `--steps` accepts integers 1 through 16; default 1.
- Default random K/U and tagged state match P2 for step zero. Later K/U and
  row/CTA-dependent g vary with time. Shorter runs use the same sequence prefix.
- Every warmup or timed launch restarts from immutable `S_0`; timing iterations
  do not feed the previous launch's output into the next launch.

The recurrence loop is not unrolled over steps, so all step counts use one
compiled kernel and the same static register footprint. The persistent S
fragment contains 128 FP32 values/thread. Product values are read from TMEM
in chunks of 16 values/thread and immediately applied to S. This bounds the
temporary accumulator lifetime and avoids spilling the persistent state.
The first copy-atom mode is preserved when slicing the TMEM partition; no
assumption equating thread ID with row ID is introduced.

The MMA resets to `ScaleOut::Zero` each step. One completion commit per step
uses barrier parity `step & 1`. Shared-memory proxy fencing orders operand
staging, and a TMEM-load wait plus cross-thread fences/barrier orders the
readers before the next MMA overwrites the allocation. See NVIDIA's
[tcgen05 synchronization primitives](https://docs.nvidia.com/cutlass/latest/media/docs/pythonDSL/primitives.html).

## Build and measure

Build on B300 with CUDA 13.0 and CUTLASS headers:

```bash
nvcc -std=c++17 -O3 -lineinfo -arch=sm_103a \
  --expt-relaxed-constexpr --expt-extended-lambda \
  --ptxas-options=-v,--warn-on-spills -Icutlass/include \
  experiments/sm100_phase6/tcgen05_p3_recurrence.cu \
  -o experiments/sm100_phase6/tcgen05_p3_recurrence

./experiments/sm100_phase6/tcgen05_p3_recurrence \
  --steps 1 --warmup 30 --iters 200 --batch 1024
```

The executable reports `launch_us = T(N)` and `update_us = T(N)/N` for the
whole batch, along with correctness and resource attributes. These are not
single-CTA latency measurements. Spill counts come from the PTXAS build log.

Run all five lengths in five interleaved rounds (reversing alternate rounds):

```bash
python experiments/sm100_phase6/benchmark_p3.py
```

The runner defaults to steps `1 2 4 8 16`, warmup 30, iterations 200 and
batch 1024. It saves each command, output and validated record in
`build/p3_results.json`, stops on failure, and prints mean `T(N)`, mean
`T(N)/N` and the sample standard deviation of `T(N)/N`. Use `--dry-run`
to inspect commands. It invokes no profiler.

## Correctness and local validation

The CPU reference computes each step's product in double precision from the
actual BF16 operands, then evaluates the scalar recurrence, rounding state
to FP32 after every step. All CTA outputs are checked, with
`atol=rtol=1e-5` for multi-step cases; existing deterministic single-step
cases require exact equality. State and decay inputs are checked for mutation.
This experiment preserves FP32 state across steps; it does not reproduce
production K2's intermediate BF16 state rounding or its other phases.

`check_p3_layout.cu` provides a host-only layout check over all 128 threads:
it checks one-to-one coverage of all 16,384 output values, row-wise decay,
register grouping, and every chunk's TMEM address against the original
unsliced partition. It includes the actual P3 source and launches no CUDA
work. Compile with the same flags as above, using `check_p3_layout.cu` as
input and a separate executable path. This cannot establish GPU numerical
correctness or synchronization correctness.

The host-only check passed locally: 128 threads, 16,384 output values covered
exactly once, and 524,288 TMEM source addresses checked. Python syntax and
the five-length command-generation dry run also passed.

Local CUDA 13.0 / `sm_103a` compilation (MSVC, cached CUTLASS) reports:

| Metric | P3 |
|---|---:|
| registers_per_thread | 226 |
| dynamic_smem_bytes | 8320 |
| spill stores / loads, bytes | 0 / 0 |
| stack frame, bytes | 0 |
| correct | Unverified on GPU |
| launch_us / update_us | Unmeasured |

Build log: `build/tcgen05_p3_recurrence_build.log`. The local timing sweep
stopped at its first `steps=1` invocation: `cudaGetDevice` returned
`CUDA error: (null)`, exit code 1, before any kernel launch. The local GPU
is an RTX 4060 Laptop, not SM100/SM103. No NCU run was made.

Evaluate amortization against P3's own `steps=1` baseline: its 226 registers,
chunked product reads and loop synchronization differ from P2-epi. A falling
`T(N)/N` supports further integration work, but neither convergence to P0
nor a full-K2 speedup is guaranteed by this isolated experiment.
